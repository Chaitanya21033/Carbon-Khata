# Design decisions

Each entry gives the choice and the reason. These were judgement calls made during the build: the owner asked for sensible defaults without being asked each time.

| # | Decision | Reason |
|---|---|---|
| D1 | The prototype moved to `reference/` and still runs (`npm test` → 38 passing) | It is the functional spec. Keeping it runnable lets anyone diff behaviour |
| D2 | The ledger keeps the prototype's **quantity-register** semantics: signed lines opening / received / issued / closing / reading / adjustment, with corrections as reversal + new entry. Each row also stores a derived `direction` (in / out / stock / reading). True **paired** lines are used where two parties exist: cluster exchange lines (sender weighbridge vs receiver weighbridge) and the credit split (credits share + OEM-claim share = 1) | Full debit/credit pairs on every stores line would change every query and break the 38 ported tests without adding information. Pairing is where double counting can actually happen |
| D3 | **Bit-exact port** of the seeded generator: mulberry32 with `Math.imul` / `>>>` semantics, JS `Math.round` and `toFixed` | The planted data errors land in exactly the same months, so the reference tests port 1:1. A golden test compares all 1,448 seed lines and 26 issue messages (English and Hindi) with the TypeScript output |
| D4 | EMS split along the real boundary: **decision + accounting + naive twin in the API** (`EmsBrain`), **asset physics in the site controller** (`sim/simulator/site.py`) | The product must work the same with real devices. In a real plant a PLC or inverter controller executes setpoints. An in-process integration test wires both halves and reproduces the prototype to the rupee: ₹26,579 vs ₹32,880 (−19.2 %), evening −66.2 %, peak 380 kW |
| D5 | **Plant clock** comes from telemetry. The site controller asks for a plan (`ems/request`) at each 15-minute block boundary. APScheduler still runs a wall-clock 15-minute job for real-time pull-only sites, plus hourly weather/market and minute-by-minute state saving | A wall-clock job cannot keep up with a 60× simulator. Driving the cycle from telemetry makes the product clock-agnostic |
| D6 | Plant-local time kept as "IST wall-clock ms" inside the twin and EMS. ISO `+05:30` on the wire and in the database | The prototype treated UTC hours as local hours. Keeping that convention internally keeps the maths identical, while stored timestamps stay correct |
| D7 | Packet-level checks (V01 "5× typical", V10 duplicate slip, V12 negative stock, V11 meter going backwards) moved from the simulator to the **API ingestion path** | They are product rules. The simulator now sends raw data only, so a typo injected from the control panel is held by the product |
| D8 | **Passports are issued by the API**. The line posts production events (started / moved / finished). The twin attributes each 1-minute sub-meter reading to the bodies at each station, using the prototype's rule | Same numbers as the prototype, from product-side data. One passport per finished body, total = S1 + S2 + steel (tested) |
| D9 | **Steel factors**: the library keeps `EF_STEEL_IN_REF` 2.2 t/t as the generic Scope 3 reference. Passports use versioned per-OEM factors (`oem_steel_factor`: A/B 2.3, C 1.55 kg/kg) | Both values came from the inputs. They serve different purposes (Scope 3 inventory vs OEM-specific mill certificates) |
| D10 | **Smart meters instead of Claude vision**, per the owner. The meter card pulls the register from the meter feed or head-end API (`GET /meters/{id}/latest`). Bills are uploaded, pre-filled from the meter feed, and the custodian types and confirms the amount | Owner's instruction. `SMART_METER_API_URL/KEY` plug in a real head-end system. No Anthropic key is needed |
| D11 | **Electricity Maps is adapter-only** until the owner adds a key (`ELECTRICITYMAPS_API_KEY`). Until then the UI shows "needs key" and uses the CEA factor | Owner's instruction |
| D12 | IEX and GSTIN/Udyam are adapter + mock. The IEX mock replays the prototype's 96-block market shape. KYB does local format and state-code checks | No public free APIs. Licensed feeds plug in behind the same interfaces (`IEX_API_URL`, `KYB_API_URL`) |
| D13 | Demo **reset** is an ops endpoint (`POST /api/v1/ops/reset-demo`), hidden from the OpenAPI schema, allowed only for a device key or admin, and switched off by `DEMO_RESET_ENABLED=false` | The control panel's "Reset all demo data" needs a way to re-seed. Disabling it by config keeps it out of any real deployment. This is the only simulator-driven route in the API |
| D14 | Batch tracing belongs to **Annapurna Foods' own tenant**, with its own login (QC manager), and to Brand A / Brand B viewers. Vardhan's users no longer see FMCG batches | The prototype showed a co-packer's data inside the body-builder's login. That breaks tenancy |
| D15 | Every cluster figure comes from ledger rows. The pool is settled per block from member meter data (`pool_block` → `pool_day`). Exchange benefits accrue per 15 minutes into `exchange_accrual`, back-filled from 1 April 2026 by the seed | The prototype seeded year-to-date figures with constants (₹4.85 L/month pool saving). The scoreboard is now a sum over rows |
| D16 | Hard-coded screen numbers removed: grid factor 0.71 → the factor library; ₹6.2 L/body turnover → a `TURNOVER_INR` financials register (dummy, seeded); "≈ 2,760 t/yr" → computed from 3 MWp × 4.5 kWh/kWp/day × grid EF × 0.9 | Brief: every number from the ledger or a documented calculation |
| D17 | Held or blocking data never reaches reports. Live holds are stored as `status = held`, which the index ignores. History lines with an **open** block-severity issue are excluded from the report index (emissions, OEM file, BRSR) until decided | Brief §10. Seed totals are unchanged, because the planted blocking issues sit on registers without emission factors |
| D18 | Factor changes insert a new version and close `valid_to` on the old one. Months use the version valid in that month | Brief §10 (tested: Sep 2026 keeps v1 and Oct 2026 uses v2) |
| D19 | The web app keeps the prototype's screens and CSS. The browser state store was replaced by `state/store.tsx` with the same `s / d / actions` interface, backed by `GET /workspace` and REST actions (TanStack Query). Module constants (`REGISTERS`, `PLANT_MONTHS`, `PLANT`) became ES-module **live bindings** updated from the workspace | Minimal screen changes, so the look stays identical. The server is authoritative for issues, emissions, DQ, tariff and grid EF. The web keeps a few pure display helpers (ledger index, `monthEmissions` for charts) over ledger lines served by the API |
| D20 | The simulator is a separate Python process with its own React control panel (:5174 → control API :5175). It uses device keys and the public MQTT/REST interfaces only. A test greps the product code for simulator imports and control routes | Brief §7 |
| D21 | OTP login by e-mail. In dev the code is printed in the API console **and** returned to the sign-in screen (`OTP_DEV_ECHO=true`) so demos run without SMTP. JWT HS256, 12 h by default. Read-only support sessions are 30 minutes and audited | Brief §3. Switch off the echo and set `SMTP_URL` for real use |
| D22 | Device keys are per device (`DEVICE_KEYS` in .env) | A shared key would make every device the same tenant (a bug found in testing) |
| D23 | Optional **LP optimiser** (PuLP + CBC) behind `ems_settings.solver`: a 96-block day-ahead LP on the last 24 h of metered load, compared with the rule-based cost. Rules stay the default dispatch | Brief §3: port the rules first, then compare an optimiser |
| D24 | The audit log is append-only at the database level (trigger) and hash-chained (`GET /audit/verify`) | Tamper evidence for exports, reversals, factor and allocation changes |
| D25 | Dummy data added (all fictional, same style): users for every role; Annapurna's QC manager; Brand A/B quality teams; the "Adityapur Green Cluster (demo)" name; cluster history from 1 Apr 2026; a dummy turnover register. Domains use `.example` | Brief §12 |
| D26 | **No-Docker mode**: `DATABASE_URL=embedded` starts real PostgreSQL from the `pgserver` pip package, with its data in `%LOCALAPPDATA%` (outside a project path that may contain spaces). `MQTT_ENABLED=false` sends the same meter topics over `POST /ingest/messages`. `setup.ps1` picks this mode when Docker is not running | The owner did not want to install Docker yet. Keeping PostgreSQL (not SQLite) means the schema, triggers and every test behave the same |
| D27 | Field devices: 12 sensors including 3 CO₂ analysers (genset stack, oven flue, welding-bay air). Each has a device API and its own page in the simulator app (`#/device/<id>`), where it can be overridden or taken offline. The product sees only the reported readings (`/api/v1/sensors`) and checks them: an air-CO₂ action level, analyser vs metered-kWh drift, and silent devices | Shows mature device handling: reading, history, plausibility checks against metered energy, and outage detection, without the product trusting a single sensor |
| D28 | Phones on the LAN: Vite listens on all interfaces, and phones reach the API through the same origin (`:5173/api`), so only ports 5173 and 5174 need to be open. `GET /system/network` gives the laptop IP for the **Open on phone** QR and for part/batch QR codes | One address per app, no CORS or HTTPS set-up for a Wi-Fi demo |
| D29 | Uploads from phones are saved on the server machine in `captures/<date>/` with readable names (time, kind, user, slip number), deduplicated by SHA-256 (V10), audited, served only to the plant tenant (`/documents/{id}/file`), and pushed to dashboards over SSE | The demo shows a phone capture arriving on the laptop dashboard immediately, with the file kept on the laptop |
